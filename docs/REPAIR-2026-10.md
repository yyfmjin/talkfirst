## 6. 下一步验证清单（在可用环境里按序执行）

### 6.0 启动相关：两个必须先知道的坑（本轮实测发现）

**坑 1：`dist/` 是提交进仓库的构建产物，且已经过期。**
`apps/api/dist/` 里有 97 个 `.js`，但**没有** `common/security-config.js`、`common/connection-guard.js`、`admin/admin-public.decorator.js`、`auth/auth-password-reset` 相关产物，`admin.controller.js`、`moments.controller.js`、`social-safety.controller.js` 也都是旧版本。
→ **`start-local.bat` 跑的是 `node apps/api/dist/main.js`，也就是"当前源码的上一版构建"。**
→ 现象会是：**修好的 bug 在"重启后"依然复现**，因为根本没跑到新代码。
→ 因此本仓库新增了 `start-local-dev.bat`：它在启动前先 `npm run build -w @talkfirst/api`，并在构建失败时**直接退出**（而不是继续用旧 dist）。

**坑 2：配置校验发生在 `ConfigModule` 读取 `.env` 之前（本轮修复）。**
Phase A 引入的启动守卫（`assertSecretConfigured` / `assertThrottleMultiplierSafe`）运行在 `NestFactory.create(AppModule)` **之前**，而把 `.env` 灌进 `process.env` 的正是 `AppModule` 里的 `ConfigModule`——它在 `create()` 内部才初始化。
→ 后果：`node dist/main.js` 看到的 `NODE_ENV` 是 undefined → 被正确归类为"生产部署" → 因 `.env` 里的占位密钥 `change-me-in-development` 而**拒绝启动**，而它从未读过那个 `.env`。
→ 修复：`main.ts` 新增 `loadEnvironment()`，在任何校验之前用 `dotenv` 显式加载 `<repo>/.env`（`dotenv` 不覆盖已存在的环境变量，所以 Docker/systemd/Shell 的真实环境永远优先，在那里是 no-op）。
→ **这正是"启动项目"在当前状态下会被挡住的根因**，且它是我在 Phase A 引入的回归，已修。

1. **P001**：`PUT /users/me/languages` 传 `[{en,NATIVE},{en,LEARNING}]` → 期望 200 且语言**不被清空**（修复前：400 `UNKNOWN_LANGUAGE_CODE` 且数据丢失）。
2. **P003**：A 移除与 B 的连接后继续发消息 → 期望 403 `CONNECTION_REMOVED`（修复前：正常发出）。
3. **找回密码**：`POST /auth/password/forgot` 对未注册邮箱 → 期望 200 `{sent:true}`；用正确验证码 `POST /auth/password/reset` → 期望 200 且**其他设备的 refresh token 全部失效**。
