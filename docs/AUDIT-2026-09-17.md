## 5. 社交账号交换安全机制（重点）

正常设计：A 发起 → B 接受 → **仅双方**看到彼此被授权的账号。

### 实测结果

| 检查项 | 结果 | 证据 |
|---|---|---|
| 未登录访问 | ✅ 已阻断 | `curl` 无 token → `Unauthorized` |
| IDOR：读他人 conversation | ✅ 已阻断 | 返回 `CONVERSATION_NOT_FOUND` |
| IDOR：读他人 messages | ✅ 已阻断 | 返回 `CONVERSATION_NOT_FOUND` |
| Block 后发送交换请求 | ✅ 已阻断 | `BLOCKED` |
| Block 后发文字消息 | ✅ 已阻断 | `BLOCKED` |
| **Block 后发图片消息** | ❌ **绕过成功** | 见下 |
| 未授权即可查看账号 | 🟡 部分 | 别人全部账号被暴露，范围见下 |
| **`visibility` 是否按"对该人"生效** | ❌ **错误** | 见下 |

### Bug A（Critical）：`visibility` 是账号级全局，不是"仅对交换对象可见"

`exchange.service.ts` 第 220-227 行，接受交换时：

```ts
await tx.socialAccount.updateMany({
  where: { userId: exchange.requesterId, platform: { in: exchange.platforms } },
  data: { visibility: "EXCHANGE_ONLY" },     // ← 把这个用户这些平台的全部账号改了
});
```

实测确认：A 与 B 在会话 1 完成交换后，A 的账号变为全局 `EXCHANGE_ONLY`。数据库实测：

```
USER A: INSTAGRAM:@exchange_alice  visibility=EXCHANGE_ONLY
        TELEGRAM:@exchange_alice   visibility=EXCHANGE_ONLY
```

配合 `sharedContacts()` 第 292 行 `where: { platform: { in: platforms } }` **按平台而非按 userId 查询**（虽有 `memberIds` 后置过滤），一旦用户有第二个会话与另一个人完成交换，其账号就会对第二人暴露。
- 与 readme §50「社交账号交换必须设置防绕过机制」直接冲突。
- 影响：越权查看他人社交账号；交换的"双向知情同意"语义被破坏。
- 根因：缺少 `SharedSocialAccount` 关联表（审计清单中该 model **不存在**），无"授权对"概念。

### Bug B（High）：图片消息不校验 Block（REST + WebSocket 双路径）

同一 block 状态下，三条路径行为不一致（实测）：

| 路径 | 结果 |
|---|---|
| `POST /conversations/:id/messages`（文字） | ✅ `BLOCKED` |
| `POST /conversations/:id/messages/image`（图片） | ❌ **成功入库** |
| WS `message.send` TEXT | ✅ `BLOCKED` |
| WS `message.send` IMAGE | ❌ **成功入库并广播** |

`social-safety.controller.ts::sendImageMessage`（约 230-255 行）与 `chat.gateway.ts::handleImageSend`（约 281-312 行）都缺少 text 路径具备的 `block.findFirst` 校验。
- 影响：被拉黑后仍可继续用图片骚扰，直接违反"被 Block 后仍然可以聊天"这条硬性验收项。
- 严重程度：**High**（安全/反骚扰核心功能失效，且用户无法感知）。

## 9. Security Audit

### Critical：1
1. **Exchange `visibility` 账号级全局**（§5 Bug A）— 越权查看社交账号，破坏双向同意语义

### High：3
2. **图片消息绕过 Block（REST + WS 双路径）**（§5 Bug B）— 反骚扰失效
3. **Discover 无 Block 过滤** — 拉黑后仍在推荐流中互相可见（`discover.service.ts` grep `block` = **0 命中**，而 chat/connections/moments/exchange 均有）
4. **无 CSRF token** — 依赖 `SameSite=Lax` 单层防护，Cookie 认证下跨站写操作有风险

### Medium：4
5. `newVerificationCode()` 使用 `Math.random()`（非 CSPRNG）生成验证码
6. login 限流 50/min 偏松，易被撞库
7. `getFullCard` 返回 `email`/`isAdmin`/`status`（当前仅 self 调用，尚无泄露；一旦复用于公开卡片即成漏洞）
8. 无 Message 已读状态，无法满足"被读"类隐私预期

### Low：4
9. 无 Redis → 单实例内存 presence，多实例即失效
10. `.env.example`(5432) 与 `.env`(5433) 端口不一致
11. 生产存储为本地磁盘 `saveLocal`，多实例不可用
12. `TranslationProvider` 外部接口未做响应大小上限

### 通过的安全项 ✅
JWT 类型校验（拒绝非 access token）、Refresh 轮换 + 撤销、密码 bcrypt、HttpOnly Cookie、生产密钥强校验（含 `change-me` 检测）、IDOR 全面防护、无邮箱泄露到公开 payload、图片 magic-byte 校验、`prisma db execute` 全部参数化。

## 14. 技术债务
