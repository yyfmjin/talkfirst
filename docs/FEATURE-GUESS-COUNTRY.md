# 猜猜看（Guess Where They're From）功能设计

> 一句话：发现页「今日剩余 20」旁边加一枚「猜猜看」，用推荐流里的真实头像出题，三选一猜 TA 的国家；答完给「打招呼」，猜对猜错都累计到被猜者的「好不好猜」。

状态：**设计稿，未实现**。写完这份之后需要你拍板 4 个问题（见第 9 节）。

---

## 1. 先说三件必须先定的事

这个功能有两个地方会让人不舒服，设计上要先处理，否则做出来是负资产。

**① 长相 ≠ 国籍。** 用真人照片让人猜「哪国人」，天然会教人按脸做判断。在语言交换产品里，这个副作用比别的产品更糟——用户来这里是为了不被刻板印象定义。
→ 做法：
- 文案不写「猜国籍/猜长相」，写「**猜 TA 从哪来**」；
- 结果页永远**先给答案**，不评判猜测（答错不出现「你错了」「正确答案是」这种措辞）；
- **不做排行榜**，也没有「最好猜的人」榜。正确率只作为一句中性信息。

**② 照片是别人的。** 把用户照片当游戏素材，必须有明确的同意与退出通道。
→ 做法：
- 只对**头像对你可见**（现有 `canViewField("avatarUrl")`）的人出题；头像设为「仅连接/仅自己」的人永不出题；
- 新增「**不想被猜**」开关（在「隐私与安全」里），关掉后立刻从出题库移除；
- 只用**头像**，不动资料相册里的其他照片（相册照片更私密，且现有相册有单独的可见性规则）。

**③ 一次猜 = 看了一张照片。** 首页只有一个「今日剩余 N」，两套额度会让人算不清。
→ 做法：**共用发现页的每日 20 次**。猜一次扣 1，`remaining` 与发现页同一个数字，不做第二套计数。

## 2. 玩法规则

| 项 | 规则 |
|---|---|
| 出题对象 | 推荐流里的候选（复用现有 weighted 匹配：语言 30 / 兴趣 25 / 目的 20 / 国家 10 / 活跃 10 / 完整度 5） |
| 每日次数 | 20 次，与发现页共用；用完显示「今天用完了」 |
| 选项 | 3 个 = 正确答案 + 2 个干扰项 |
| 干扰项怎么选 | 从「**同区域但不同国**」里取（如答案为 JP → KR / TH）。不能随机全球取，否则一眼排除两个，题目失去意义 |
| 不重复 | 同一查看者对同一目标 **7 天内不重复**；自己、已屏蔽、已举报、已拒绝过打招呼的人不出题 |
| 时限 | 一道题 10 分钟有效，过期作废且不扣次数 |
| 结算 | 首次提交即生效，重复提交幂等返回同一结果 |
| 结果 | 国家名 + 国旗 + 「TA 已经被猜中 N%」（N 统计样本 < 5 时**不显示**，防止小样本暴露） |
| 打招呼 | 无论对错都显示，走现有 `POST /connections/requests` |

### 正确率的方向（容易搞反）

「计入被猜用户的正确率」= **别人猜 TA 猜中的比例**，是目标用户的一个小标签（「你不太好猜」），**不是**猜测者的成绩。

- 存两列：`guessTotal` / `guessCorrect`，只累加在被猜者身上；
- 同一个查看者对同一目标只算一次（防刷某个人的正确率）；
- 默认**只给本人看**（在「我的」里显示「被猜中 62%」），公开需本人开启——公开一个「你很好猜」的标签，是在奖励人肉搜索。

## 3. 数据模型

```prisma
model CountryGuess {
  id          String   @id @default(uuid()) @db.Uuid
  viewerId    String   @db.Uuid          // 出题给谁
  targetId    String   @db.Uuid          // 猜的是谁
  correctCode String   @db.VarChar(2)    // 只有服务端知道
  options     String[]                   // 三个候选，顺序即展示顺序
  guessedCode String?  @db.VarChar(2)    // null = 还没答
  correct     Boolean?
  createdAt   DateTime @default(now())
  expiresAt   DateTime
  @@index([viewerId, targetId, createdAt])
  @@index([targetId])
}

// User 上加三列
guessTotal   Int     @default(0)
guessCorrect Int     @default(0)
guessOptOut  Boolean @default(false)
```

**为什么答案存在服务端**：客户端只拿 `options`，`correctCode` 绝不下发。否则抓包一次，这个游戏就没了。

**为什么单独建表而不是复用 DiscoverView**：猜有「答没答」「答了什么」两个状态，而浏览是一次性的；塞进 views 表会让配额统计和猜题统计互相污染。

## 4. API

### 4.1 取一道题

```
GET /api/v1/discover/guess
→ {
    roundId: "uuid",
    photoUrl: "https://…/avatar.jpg",
    options: [{ code: "JP", name: "日本", flag: "🇯🇵" }, …],   // 3 个，已打乱
    remaining: 17,           // 与发现页同一个数字
    expiresAt: "2026-10-25T10:10:00Z"
  }
```

无题可出（候选耗尽）→ `409 NO_CANDIDATE`；次数用完 → `429 NO_QUOTA`。

### 4.2 作答

```
POST /api/v1/discover/guess/:roundId
{ "countryCode": "JP" }

→ {
    correct: true,
    answer: { code: "JP", name: "日本", flag: "🇯🇵" },
    target: { id: "uuid", nickname: "Mia" },      // 用于「打招呼」
    stat: { total: 42, correct: 26, accuracy: 0.62 } | null,   // total<5 时为 null
    remaining: 16,
    helloState: "NONE" | "PENDING" | "CONNECTED"  // 已打过招呼就不再重复发
  }
```

错误码：`GUESS_EXPIRED`（过期）、`GUESS_ALREADY_ANSWERED`（幂等：直接返回上次结果）、`INVALID_OPTION`（countryCode 不在 options 里）。

### 4.3 打招呼

复用现有 `POST /connections/requests`，请求体加一个可选 `source: "GUESS"`（用于看这个玩法带来了多少连接）。不改现有行为，老客户端不传就走默认。

## 6. 埋点与护栏

| 指标 | 说明 | 护栏 |
|---|---|---|
| 出题→作答率 | 卡片打开后真正答了的比例 | < 40% 说明题目无聊或加载慢 |
| 答对率 | 整体正确率 | 期望 45–65%；> 80% 说明干扰项太弱，< 30% 说明太刁 |
| 答完→打招呼率 | 这个玩法对连接的贡献 | 目标 > 12% |
| opt-out 率 | 关掉「不想被猜」的比例 | > 10% 立刻下线重做 |
| 举报率 | 结果页举报该照片 | > 0.5% 立刻下线 |

## 7.5 什么人能作为题目（2026-10-25 改：邀请制）

`avatarUrl` 只是一个地址，库里没有任何字段能证明它是一张真人照片。所以资格是**组合规则**，不是单一开关：

| # | 条件 | 怎么判定 |
|---|---|---|
| 1 | 头像存在，且**对你可见** | 沿用 `canViewField("avatarUrl", viewer)` |
| 2 | 国家存在，且**对你可见** | 否则会通过游戏泄露原本隐藏的字段 |
| 3 | 资料完整 | `isProfileComplete()` |
| 4 | 账号正常 | `status = ACTIVE`，非 DEMO 行 |
| 5 | **已接受邀请** | `guessOptIn = true`（默认 false，接受邀请后才置真） |
| 6 | 头像未被判为非真人 | `avatarGuessExcluded = false`（见下） |
| 7 | 不是你自己、没互相屏蔽、没拒绝过你的打招呼 | 现有关系表 |
| 8 | 你今天没猜过他 | 7 天内不重复 |

### 为什么改成邀请制（2026-10-25）

原方案是「默认参与 + 自动人脸检测卡真人头像」。两条都放弃了：

- **同意比识别重要**。拿真人照片让别人猜「从哪来」，真正要解决的是「本人知道并同意」，
  而不是「这张脸是不是真的」。检测做得再准，也不能替代同意；
- 目标用户里有不少外国用户，对「我的照片被拿去做什么」很敏感，默认参与会直接引发反感；
- 反过来，邀请制把质量门槛交给**筛选**：我们先挑「头像公开、资料完整、头像够清晰」的人，
  推送一条邀请，接受后才进题库。人脸检测自然就不需要了。

### 现在的资格（邀请制）

**筛选 + 兜底规则（不依赖人脸识别）：**

1. **邀请**：脚本 `scripts/invite-guess.mjs` 挑人（头像公开、资料完整、头像 ≥ 400×400、账号正常、未被举报出池），
   写 `guessInvitedAt` 并发一条站内通知；重复执行不会重复打扰。
2. **接受才生效**：App 发现页出现一条横幅，接受 → `guessOptIn = true` 进题库；拒绝 → 不再邀请。
3. **清晰度门槛**：头像 ≥ 400×400（上传时记尺寸），挡住缩略图与表情包。
4. **一键自我排除**：设置里「我的头像不是真人照片」，勾了永不出题。
5. **举报即下架**：结果卡可举报，命中后 `avatarGuessExcluded = true` 立即出池。

> 自动化的人脸检测**不做了**：它解决的是「是不是真人」，而这里要解决的是「本人同不同意」；
> 而且对在意隐私的用户来说，「被算法扫脸」比「被邀请」更糟。

## 附：为什么不叫「猜国籍」

「国籍」是一个法律身份，用户资料里存的是 `countryCode`（居住/来自），两者经常不一致（留学生、旅居、双重国籍）。叫「猜 TA 从哪来」既准确，也避开了「看你长得像哪国人」这层意思。
