# 礼物（虚拟 + 实体）

> 状态：**虚拟礼物已实现并上线**；**实体礼物已定口径、暂不上线**（运营方 2026-10-06 决定）。
>
> 这份文档存在的唯一理由是：把运营方拍过的产品口径写下来，等哪天做实体礼物时不必再问一遍。

## 1. 虚拟礼物 = 送花（已实现）

运营方原话：「虚拟礼物就是送花吧，就是类似点赞那种形式的就行，**不能换成现金**。」

### 1.1 形状：与动态点赞完全同构

| 维度 | 动态点赞（既有） | 送花（本次） |
|---|---|---|
| 表 | `MomentLike` | `UserFlower` |
| 主键 | `@@id([momentId, userId])` | `@@id([senderId, receiverId])` |
| 语义 | 同一对只有一条；再点一次是**收回** | 同左 |
| 计数 | `Moment.likeCount`（冗余，事务内增减） | `User.flowerCount`（冗余，事务内增减） |
| 端点 | `POST /moments/:id/like`（toggle） | `POST /users/:id/flowers`（toggle） |
| 限流 | 60 次/分钟 | 60 次/分钟 |
| 通知 | `MOMENT_LIKE` | `FLOWER_RECEIVED`（收花人） |
| 入口 | 动态卡片 | 成员资料页（打招呼下方） |

### 1.2 几个刻意的决定

- **一对只有一朵**（复合主键）。运营方说的是「类似点赞」——点赞的语义就是一次性，
  不是「刷 999 朵」。想改成可叠加，只需把主键换成 `id` 并让计数累加，是一处小改动。
- **再点一次是收回，而不是关机**：与点赞一致，用户点错了要能自己撤回。
- **收回不发通知**：否则「点错再点一下」会在对方那里留下两条记录。
- **不能折现**（运营方明确要求）：所以它**没有**任何余额、价格、提现、流水概念 ——
  只是一条关系行加一个计数。这一点也解释了为什么它不需要钱包/账务模型。
- **朵数对能看到资料的人公开**：与动态的点赞数同一性质。它**目前**不在
  `ProfileFieldVisibility` 的逐字段可见范围里（那套白名单里没有它）；如果以后要能隐藏，
  得在白名单里加字段 + 加开关，不是加个 CSS 就完事。
- **守卫与资料页同源**：谁能看到这份资料，谁就能送花；被拉黑、目标非 ACTIVE、给自己送
  分别得到 403 / 404 / 400。不另写一套「宽松版」判断 —— 送花会给对方产生可见后果
  （计数 + 通知），宽松版就是绕过拉黑的旁路。

### 1.3 覆盖面

- 服务层单测：`apps/api/src/users/users-flowers.spec.ts`（8 条：送出/收回/计数不为负/
  给自己/被拉黑/非 ACTIVE/投影/本人视角）。
- 表与迁移已进 `apps/admin/test/smoke.test.mjs` 的静态钉（模型清单 + 迁移白名单）。

**尚未做**（有意留白，不是遗漏）：

- 后台没有专门的「花的分布」看板（后台能看到的只有 `User.flowerCount` 这个数字）。

## 2. 实体礼物（口径已定，暂不上线）

运营方原话：「实体礼物就是两个人亲密度增加到一定等级可以解锁这个功能，由用户自发邮寄，
填写快递单号邮寄到中转站，再由中转站邮寄到对方，这样一个形式，出于对隐私安全的考虑后台
可以看到完整的信息，没有上限，保证合规合法的礼物都可以。这个功能我建议先保留，先不上线，
稍微有点复杂。」

### 2.1 已定的口径

| 项 | 决定 |
|---|---|
| 解锁条件 | 两人**亲密度**达到某个等级后解锁（**阈值未定**） |
| 寄送方式 | 用户**自发邮寄**：寄件人填写快递单号 |
| 路由 | 寄件人 → **中转站** → 收件人（双方不交换真实地址） |
| 隐私 | 后端**可见完整信息**（含快递单号；运营方明确要求，用于纠纷与合规） |
| 数量 | **没有上限** |
| 内容 | 只要**合规合法**的礼物都可以 |
| 排期 | **先保留、先不上线**（运营方判断「稍微有点复杂」） |

### 2.2 真要做之前必须先定的（现在没定，也不要替产品猜）

1. **亲密度是什么**：现在仓库里**没有**亲密度这个量。可用的现有信号只有
   连接状态、消息往来、共同兴趣/语言 —— 亲密度要么由这些派生（需要一个公式 + 权重），
   要么新开一张 `Intimacy` 表逐步累加。这是产品决定，不是实现细节。
2. **解锁阈值**：等级怎么分、多少算够。
3. **中转站是谁**：运营方自己的收货点？第三方仓？这决定后台要不要录入中转站地址、
   谁能看到地址。
4. **谁付运费**、**丢了/退回了算谁**、**双方能否取消**。
5. **合规筛查**：违禁品怎么拦（人工审核？申报品类？），以及需要留存多久的邮寄记录。
6. **收件人怎么确认收到**（双方互评？快递签收？）—— 这一条会决定要不要一个订单状态机。

### 2.3 实现时的数据形状（预案，未落地）

按 2.1 的口径，最小可行形状大致是：`GiftOrder`（寄件人、收件人、中转站、快递单号、
状态机、时间戳）+ 后台审核入口；**收件地址不落成员可见的字段**（只在中转站与后台可见）。
在 2.2 的六个问题定下来之前，不要先建这张表 —— 状态机会被猜错。
