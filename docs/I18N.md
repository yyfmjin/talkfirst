# 双语（中 / EN）约定

> 2026-10-19 收口。这份文档回答三件事：**文案放哪、组件怎么取、怎么防止回退**。

## 1. 唯一的事实来源

- 词典：`apps/web/src/lib/i18n/dictionary.ts`，`export const zh` / `export const en` 两份同键对象。
- `MsgKey` 由 `zh` 推导，**漏了 en 会直接编译失败**，这是刻意的。
- 页面语言来自 URL（`/en/...`），`useLocale()` / `currentLocale()` 只是读这条规则。

## 2. 四种取文案的场景（选错就会在英文界面看到中文）

| 场景 | 写法 | 例 |
|---|---|---|
| 客户端组件 | `const { t } = useT();` | `app/moments/settings/page.tsx` |
| 模块级常量表 / 纯函数 | 存 **`MsgKey`**，渲染时 `t()` | `lib/profile.ts`、`lib/attribute-sections.ts`、`lib/chat-socket.ts` |
| 非组件代码（api 层、Server Component） | `t(currentLocale(), key)` | `lib/api.ts`、`app/register/success/page.tsx` |
| 站点 metadata | 每个语言一份 layout，各自 `t("zh"/"en", "meta.*")` | `app/layout.tsx`、`app/en/layout.tsx` |

**不要**把中文句子放进模块级常量：那是个拿不到当前语言的字符串，英文界面会原样显示它。

## 3. 踩过的坑（每条都真实发生过）

1. **JSX 文本节点不是字符串**。只扫引号的脚本会漏掉 `<p>还没有视频</p>`，于是「只剩 2 个文件」其实还有十几处。`scripts/i18n-scan.py` 两类都扫。
2. **键前缀会撞车**。会话详情用过 `ms.`，与「动态同步设置」的 `ms.` 冲突（`ms.title` 等）。词典插入脚本有重复键断言，直接拦下——加键前先想好命名空间。
3. **测试会按中文文本断言**。`profile.spec` 用 `getByLabel("昵称")`、`chat-socket.spec` 认「实时连接」，所以 zh 侧必须逐字保留，翻译只写进 en 侧。
4. **`ui-copy` 测试要求 `label` 等属性是词条而不是英文**。字段名若叫 `label` 而值是 `"fb.kindBug"`，会被判成「未翻译英文」；改叫 `labelKey` 才表达清楚。
5. **`.replace("例如：", "")` 这类取巧在多语言下必坏**：英文没有这个前缀。占位符要单独建键。
6. **`html lang` 仍是 `zh-CN`**。英文页由客户端的 `HtmlLang` 改，服务端首字节不是 `en` —— 这是已知取舍（见 `app/en/site/page.tsx` 注释）。

## 4. 防回退

```bash
python scripts/i18n-scan.py      # 0 处 = 干净；退出码 1 表示还有待办
npm run i18n:scan                # 同上（根 package.json 已接）
```

允许清单只有三类，且都在脚本里写明理由：

- `lib/i18n/*`、`lib/errors.ts` —— 词典本身；
- `HOT_TOPICS`（旅行/美食/…）—— 对外展示的话题**内容**，不是界面文案；
- `"中文"` —— 语言自称，英文界面也该显示「中文」。

## 5. 覆盖范围

- web 成员端：**全部页面与组件**（本文件躺平时为 0 处硬编码中文）。
- 移动端：自有词典 `apps/mobile/src/lib/messages.ts`，机制不同但同一原则。
- 服务端下发文案（通知 title/body、验证码邮件、接口 message）仍以中文为主 —— **尚未双语**，见 `TODO` 项。
