## 0. 先说最重要的一件事：失败数不是可靠指标

同一个 desktop project，三次运行给出**三个不同的失败集合**：

| 运行 | 失败 | 失败组合 |
|---|---|---|
| 全量（修 oauth 前） | 11 | moment-detail 585/607/624、notification 648/672、profile 129、oauth-signin ×3、chat-socket 86、moment-compose 200 |
| 全量（修 oauth 后） | 9 | moment-detail **656 ×3**、notification 672、profile **92/110/129**、chat-socket 86、moment-compose 200 |
| 只跑 moment-detail + notification | 3 | moment-detail **1166/1191**、notification **145** |

**同一批 spec，换一次运行就有不同的用例倒下。** 所以：

- 看到 E2E 失败数变化（哪怕 ±5）**不能**推断代码回归；
- 反过来，某次运行里"全绿"也**不能**推断没问题；
- 判断回归要靠**隔离单跑那一个 spec**，而不是全量数字。

这一条比下面任何一条都重要，因为它是"这个门禁能不能信"的前提。

## 3. 漂移的怀疑方向（未验证）

- `profile.spec.ts` 在同一轮里从 1 条失败变成 3 条（多出 `:92` 地区、`:110` 简介），
  说明它**最先被污染**——它是全量运行里较早的一批 spec，且会写真实数据库。
- 怀疑点：共享数据库 + 共享夹具账号 + 前一个 spec 留下的状态；Playwright 默认全并行，
  而这些 spec 会互相读写同一批用户与动态。
- **未验证的候选措施**（留待后续，勿当结论）：给会写库的 spec 加 `fullyParallel: false`、
  或给每个 spec 独立的夹具邮箱/账号前缀。上一次"独立前缀"的做法已在
  `admin-*` 系列里用过，可作参考。
